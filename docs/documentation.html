1. Executive Summary & Project Purpose

ACUMEN (AI-Driven Code Understanding & Monitored Examination Network) is a state-of-the-art, secure, and distributed cloud testing platform designed for Silver Oak University to conduct both theoretical Multiple Choice Question (MCQ) examinations and practical software programming laboratory assessments at university scale.

1.1 Problem Statement

Traditional university exams and legacy web testing portals suffer from major architectural flaws:

  • Vulnerability to Academic Dishonesty: Students can switch browser tabs, search solutions with AI tools, copy-paste snippets, or blur the exam window without penalty.
  • Manual Programming Evaluation Overhead: Grading hundreds of coding lab submissions across multiple languages (Python, Java, C++, C, JavaScript, PHP) is labor-intensive and inconsistent.
  • Server Lag Under Peak Loads: Monolithic architectures crash or severely lag when hundreds of students load questions or submit exams at the exact same second.
  • Complex Role Management: Inadequate separation between Super Administrators (department directors), Faculty Admins (professors), and Students.

1.2 Core Objectives & Solution Delivered

Key Engineering Solutions Built in Version 2.0:
  • Edge-Cached Frontend: Deployed on Cloudflare Pages global Edge CDN for sub-50ms worldwide asset delivery.
  • Zero-Polling Client Engine: Exam timers, questions, and UI state run locally in React state, maintaining near-zero server load during exams.
  • Strict Anti-Cheating Protocol: Real-time browser event listeners immediately disqualify any student who switches tabs or blurs their active window.
  • 3-Tier Practical Evaluation: Multi-sandbox code execution with Judge0 CE, Google Gemini 1.5 Flash / GPT-4o-mini AI review, and offline AST heuristic grading.
  • Enterprise RBAC: Dedicated portals for Students, Faculty Admins, and Super Administrators with server-side pagination, chronological exam ordering (newest on top), and optimized MongoDB indices.

2. High-Level System Architecture & Tech Stack

The system is architected as a decoupled, cloud-native application separating client presentation, REST API orchestration, sandboxed execution, and persistent database storage.

3. Role-Based Access Control (RBAC) & User Management

The platform implements a strict 3-tier Role-Based Access Control hierarchy stored in the database and enforced on every API request via signed JSON Web Tokens (JWT).

  • Launch examination window with fullscreen & integrity guard.
  • Submit answers (MCQ selection or live code input).

  • Full system oversight and university-wide analytics.
  • Manage Faculty / Admins (Create, update, delete, reset passwords).
  • Manage Student Accounts (Server-side paginated list, search, block/unblock, password reset).
  • Manage Courses and Global Subject Catalog.
  • Audit system logs and security infractions.

3.1 Authentication Workflow

  1. Client submits credentials via POST /api/auth/login.
  2. Backend queries User collection by enrollment number. If isBlocked === true, authentication is refused with HTTP 403.
  3. Bcrypt compares supplied password against the salted database hash.
  4. Upon success, the server issues a signed JWT containing { id, enrollmentNumber, role, course, semester }.
  5. The frontend stores the JWT and dynamically renders the appropriate layout (Student Portal, Faculty Admin Portal, or Superadmin Portal).

4. Examination Engine & Workflow

The examination engine handles scheduling, question randomization, secure exam delivery, and auto-submission.

4.1 Exam Scheduling & Configuration

When an Admin creates an exam via POST /api/admin/exams, the following attributes are configured:

  • Program & Semester: Students only receive exams matching both their registered course (e.g. MSCIT, MCA) and current semester.
  • Subject Selection: Dropdown dynamically shows the program name and semester alongside the subject (e.g., React (MSCIT Sem-3)).
  • Exam Type: mcq or practical.
  • Questions Per Student: For practical exams with large question pools, admins can specify how many random questions each student receives (e.g., pool of 10 questions, each student gets 2 random questions).
  • Result Publishing Date: Precise date and time when scores and solutions become visible to students.
  • Chronological Ordering: Exams are sorted with the newest created exams at the top, and older exams at the bottom.

5. Security, Anti-Cheating & Integrity Guard

Academic integrity is preserved via a multi-layered client-and-server monitoring guard built directly into the exam-taking component.

Strict Disqualification Policy: Tab Switching & Window Blur

In accordance with university regulations, any attempt to navigate away from the active examination window results in immediate, irreversible disqualification.

5.1 Real-Time Anti-Cheat Mechanisms

Mechanism Event / Trigger System Response
Tab Switch Detection document.visibilityState === 'hidden' or visibilitychange Instantly triggers auto-submission with status: 'disqualified' and records reason "Student switched tabs or navigated away from the exam".
Window Blur Detection window.onblur Triggers disqualification if the browser window loses focus (e.g. opening another application, DevTools, or split-screen).
Fullscreen Enforcement document.fullscreenElement Exam initiates in full-screen mode; exiting prompts immediate warning/submission.
Clipboard Protection copy, paste, cut, contextmenu Disabled across all question text and code editor areas to prevent pasting external code or copying questions.
Random Question Allocation MongoDB aggregation with $sample Each student receives a distinct randomized subset of questions from the subject pool.
Single Submission Lock Unique compound index { examId: 1, studentId: 1 } Prevents double submissions or race conditions at the database level.

6. Practical Code Execution & 3-Tier AI Grading

Practical coding examinations require sophisticated execution and evaluation beyond simple string matching. The platform incorporates a 3-tier grading pipeline designed for maximum resilience.

6.1 The 3-Tier Evaluation Pipeline

  1. Tier 1 — Isolated Sandbox Execution (Judge0 CE):

    Student code is compiled and executed in a sandboxed container via the Judge0 CE API against predefined test cases (inputs and expected outputs). Execution time, memory consumption, compile errors, and standard outputs are captured.

  2. Tier 2 — AI Semantic & Structural Review (Gemini / OpenAI):

    If an API key (GEMINI_API_KEY or OPENAI_API_KEY) is configured, the code is evaluated for algorithmic correctness, code quality, edge-case resilience, and similarity to the model answer. Generates constructive, human-readable feedback for the student.

  3. Tier 3 — Heuristic AST Pattern Fallback:

    If external APIs or sandboxes are unreachable, an offline language pattern analyzer inspects code syntax (loops, functions, classes, JSX components, event handlers) using language-specific weight profiles, ensuring no submission ever fails or hangs.

Language Execution Mode Heuristic Pattern Weights
Python / C / C++ / Java Judge0 Sandbox (stdin/stdout) Syntax validation, function definition, control flow, loops
JavaScript (Node) / PHP Judge0 / Local Sandbox ES6 syntax, functions, algorithms, data structures
React / JSX / HTML / CSS Non-executable (Client-side static) Component structure (25%), React hooks (30%), code quality (25%), complexity (20%)

9. Concurrency, Load Capacity & Lag Prevention

Rigorous architectural analysis was performed to verify system performance under high simultaneous user loads.

9.1 Concurrency Capacity Matrix

Exam Type Active Concurrent Students Simultaneous Submissions / Sec Observed Latency / Behavior
MCQ Exam 1,000 – 2,000 Students 60 – 100 req/sec Zero Lag (< 40ms). Questions and timers run locally in React. Submissions are lightweight DB writes.
Practical Exam (Coding) 300 – 500 Students 15 – 30 code runs/sec 1 – 2 seconds per submission due to Judge0 execution queue and AI grading pipeline.

9.2 Key Lag Mitigations Implemented

Architectural Optimizations in Codebase:
  • Client-Side Zero-Polling: During the 30–60 minute exam, students generate 0 network traffic. The server remains idle while students think and write code.
  • Database Connection Pool: Mongoose configured with maxPoolSize: 50 and minPoolSize: 2, preventing database starvation during submission spikes.
  • Query Optimization: All exam listings, subjects, and student dashboards use .lean() queries, bypassing heavy Mongoose document hydration.
  • Gzip Compression: Backend uses compression() middleware, reducing response payloads by ~70%.
  • Cloudflare Edge Caching: Frontend bundle (136 kB gzipped) is distributed globally with infinite edge caching, easily sustaining 10,000+ simultaneous page loads.

  1. Pre-Warming the Server (10-Minute Rule): Render free tier spins down idle instances after 15 minutes. Faculty or administrators should log into the portal 10 minutes prior to exam start to ensure the backend is fully awake and hot.
